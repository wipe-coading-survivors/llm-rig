# COORDINATOR.md

Процессные правила работы под superpowers. Применяются только к основной
сессии (координатору; в терминологии superpowers — controller). Суб-агенты
действуют по скиллам и своему dispatch; этот файл для них не инструкция.

- **stage-tag.** Перед стартом крупного этапа (заголовок в `TODO.md`,
  полный пайплайн) координатор ставит тег `before-stage-<NNN>` на HEAD
  точки интеграции (`main`) до первого коммита этапа. NNN — номер этапа,
  дополненный нулём до трёх знаков (`before-stage-024`); формат
  фильтрует тег-набор без перекрытий (stage-2/22/222). Зачем: состояние
  до этапа поднимается/сравнивается без поиска по истории — внешние
  зависимости (например, доступность/версионирование NVIDIA fedora-rpm-
  репо) могут необратимо измениться в течение этапа. Мелкие фиксы
  (мемо) — без тега.
- **planning.** Невидимых изменений нет: каждое изменение кода/сборки
  прослеживается до документа — спеки, плана или конкретного пункта `TODO.md`.
  Крупные этапы — пронумерованные пункты секции `## Этапы` в `TODO.md`
  (идентификатор — номер этапа, уровень заголовка не важен) и новые функции —
  полный пайплайн:
  брейншторм (superpowers:brainstorming) → спецификация
  (`docs/superpowers/specs/`) → план реализации (`docs/superpowers/plans/`)
  → исполнение. Дебаг и фиксы — сначала superpowers:systematic-debugging;
  если фикс нужен, он документируется (спека или план; для мелкого фикса
  достаточно мемо — правило `memo`). Исключение — только при явном указании
  пользователя. Артефакты версионируются вместе с репо.
- **memo.** Изменение существующего кода (Makefile, `scripts/`,
  containerfiles) вне плана этапа — мемо
  `docs/superpowers/memos/YYYY-MM-DD-<тема>.md`: до начала работы — контекст,
  решение, затронутые файлы; после — результаты верификации и девиации.
  Коммиты изменения ссылаются на мемо; для «мелкого фикса» из правила
  planning мемо и есть «короткий документ». Изменения только документации
  (AGENTS.md, TODO.md, отчёты) и чисто аддитивные файлы мемо не требуют.
- **execution.** Исполнение плана — superpowers:subagent-driven-development
  (свежий суб-агент на задачу + ревью).
- **workspace.** Изоляция workspace — по superpowers:using-git-worktrees:
  предложить изолированный worktree; решение за пользователем.
- **plan-fix.** Ошибка в плане, найденная при исполнении: координатор решает
  по механизму SDD (ruling → ledger, re-dispatch c ruling) и дополнительно
  обновляет документ плана/спеки, коммитя отдельно. Формат сообщения:
  `docs: <что за дефект>, [на что влияет,] <как исправлено>`.
- **finish.** Интеграция завершённой ветки — по
  superpowers:finishing-a-development-branch.
- **close.** После finish координатор: (1) отмечает чекбоксы завершённых
  пунктов `TODO.md`, (2) составляет отчёт в
  `docs/superpowers/reports/<имя-плана>.md`. Отчёт — заметка для возврата к
  основным действиям без поднятия полного контекста: что сделано (задачи,
  коммиты, интеграция), результаты верификации, девиации, rulings. Отчёт
  пишется из контекста координатора: к этому моменту workspace SDD (ledger,
  briefs, review-пакеты) уже удалён, rulings берутся из финального сообщения
  SDD. Оформление может быть передано суб-агенту, если координатор передаёт
  ему полный контекст. Координатор предлагает пользователю ревью и коммит
  отчёта. Отметка `TODO.md` и отчёт — не задачи плана: шаги плана не должны
  отмечать `TODO.md` и не должны писать отчёт.
