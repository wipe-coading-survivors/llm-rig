# Верификация cache-ram (вытеснение/restore) на живом контейнере

Дата: 2026-09-02. TODO-пункт 23: «cache-ram: вытеснение/restore — верификация на живом контейнере».

## Итог

1. **RAM-пул 128GB (`cache-ram = 131072`) — работает.** Restore после
   вытеснения слота идёт без ре-префилла: 134 tok дельты за 7.9 с против
   ре-префилла 126752 tok за 200.6 с на 64GB (~27×). Три крупные сессии
   (180k + 169k + 133k токенов) сосуществуют без единого эвикшна; пул
   ~60GB из 128GB.
2. **VRAM-потолок: `ctx-size 430000` (2×215k) — рабочий максимум.**
   `470000` (2×235k) — OOM **в обоих режимах** (unified: 459 MiB-чанк на
   device 2, 8 попыток; non-unified: 297.52 MiB-чанк на device 2). Потолок
   не зависит от режима: суммарный KV-тензор идентичен (unified:
   `n_stream=1 × 470016`, non-unified: `n_stream=2 × 235008` —
   `llama-kv-cache.cpp`, `n_stream(unified ? 1 : n_seq_max)`).
3. **`kv-unified` — не нужен** для двух тяжёлых юзеров: restore-путь
   идентичен (RAM-пул общий), non-unified даёт честный per-slot LRU.
   Плюс под unified при давлении на пул сервер сам purging-ит idle-слоты
   (`try_clear_idle_slots`), а под non-unified — нет.

## VRAM-бюджет (5×RTX 3060 12GB, tensor-split 1,1,1,1,1)

- Суммарно: weights 30 + KV 15.4 (430k) + logits ~10 (2×f32-матрицы
  vocab×hidden, target+draft) + SSM 0.3 + graphs/NCCL/CUDA-ctx ~2.5 =
  **58.3/60 GB** (калибровка: расчёт 58.2 vs замер 58.3).
- На GPU: 12 GB − ~8.7 GB overhead (6 weights + 2 logits + ~0.7 прочее)
  → KV-бюджет ≈ 3.1–3.2 GB/GPU. KV на токен (q8_0 K+V, target+draft)
  ≈ 35.8 KB → 430k = 3.08 GB/GPU (влезает), 470k = 3.37 GB/GPU (не
  влезает).
- Интерполяция: теоретический потолок ≈ 450–455k; проба нецелесообразна
  (+1.43GB KV на 40k токенов при марже 0.5–1.5GB — любой исход на
  грани, а цена — рестарт живого сервера).

## Факты для будущего

- `common_fit_params: ... llama_params_fit is not implemented for
  SPLIT_MODE_TENSOR, abort` — авто-фит параметров под свободную VRAM в
  llama.cpp (sha 69320fef) не работает с tensor-split; автоматической
  защиты от OOM на старте нет.
- `n_ctx_seq > n_ctx_train (262144)` — штатное предупреждение и для
  430k (модель работает за пределами обучающего контекста).
- Если понадобится больше ctx: K q4_0 (KV −50% ≈ +120k токенов, цена —
  качество), либо выключить MTP draft (−0.9GB ≈ +25k, цена — скорость).
  `--swa-checkpoints` на VRAM не влияет (только размер энтри в RAM-пуле).
- Наблюдение (юзер, 2026-09-02): при равном ctx unified-кеш занимает
  чуть больше VRAM, чем раздельный. Сумма основного KV-тензора в обоих
  режимах идентична (`n_stream=1 × N` vs `n_stream=2 × N/2`,
  `llama-kv-cache.cpp`), так что разница — во вторичных аллокациях
  (метаданные ggml-контекстов, гранулярность meta-бэкенда, шаринг
  ячеек draft↔target; оба OOM'а 470k произошли в конструкторе
  `llama_kv_cache` MTP draft-контекста). Практического значения нет:
  470k не встаёт ни в каком режиме.
