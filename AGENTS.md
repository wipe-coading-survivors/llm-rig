# AGENTS.md

## О проекте

Набор контейнеризированных компонентов для AI-сервера:

- модули ядра (nvidia kmod);
- драйверы юзер-спейса;
- утилиты по настройке для карт NVIDIA;
- рантаймы AI — llama.cpp, ollama;
- девелоперское окружение jupyter.

Сборка — через `Makefile` + `*.containerfile` (контейнерный инструмент —
правило **no-cre-hardcode**).

## Приоритет правил

При конфликте этих файлов со скиллами superpowers — приоритет у скилла.
Файлы добавляют требования репозитория, не переопределяя процесс скиллов.
Правила имеют устойчивые имена (без нумерации): планы, брифы и dispatch
ссылаются на правила по имени.

## Кодовые правила (для всех: координатор и суб-агенты)

Действуют при любой работе в репозитории — со скиллами и без.

- **no-cre-hardcode.** Контейнерный инструмент определяется переменной `CRE`
  (`podman` или `podman-remote` — сборка может идти через хост). В тестовых
  скриптах не хардкодить `podman`/`podman-remote`: инструмент определяется так
  же, как в Makefile — `podman` с суффиксом `-remote`, если существует файл
  `/run/.containerenv`.
- **rm-rf-guard.** В shell-коде, который мы пишем (рецепты Makefile, `scripts/`),
  `rm -rf` по пути из переменной — только через `scripts/safe-rm`:
  ```sh
  safe-rm --under ROOT TARGET...
  ```
  Хелпер (мемо `docs/superpowers/memos/2026-08-22-safe-rm-guard.md`): только
  абсолютные пути; таргет удаляется, только если он равен ROOT или лежит под
  ним; таргет, являющийся точкой монтирования (включая `/`), никогда не
  удаляется; все таргеты проверяются до первого `rm`; нет `findmnt` — отказ. В
  рецептах Makefile пути собирают из `$(CURDIR)`, не из CWD. Зачем: при
  `CRE=podman-remote` рецепты исполняются на хосте, а в toolbx хостовая ФС
  смонтирована в `/run/host` — опасна не только переменная, дающая `/`, но и
  любой mount point (`/run/host/var`, NFS-шары с модельками и т.п.) и
  относительные пути при «не том» CWD. `rm -rf` по конкретному литеральному
  пути (например, `rm -rf /app` в containerfile, `rm -rf empty` в Makefile)
  ограничением не запрещается.
- **pkill-self-guard.** `pkill -f <паттерн>`/`killall` — паттерн входит в
  командную строку процесса, исполняющего pkill (шелла самого рецепта/скрипта)
  → он убивает себя, остаток рецепта не выполняется (live 31.08: `pkill -f
  "systemd --user"` в зачисточном рецепте убил шелл, инструмент задемпировал,
  артефакты пришлось убирать отдельной командой). Правильно: убивать по PID
  (сохранить `$!`/pidfile при spawn — `kill "$(cat <pidfile>)"`), либо
  self-match-исключающий паттерн `pkill -f '[s]ystemd --user'` (скобочный
  паттерн не совпадает с собственным литералом), либо `pgrep` → фильтр →
  `kill`.
- **english-commits.** Сообщения коммитов git — на английском.
- **no-inline-comments.** В Containerfile нет завершающих (inline) комментариев
  после инструкции — комментарий только отдельной строкой. Для `FROM`
  podman/buildah отклоняет строку outright (`Error: FROM requires either one
  argument, or three`) — и в `podman`, и в `podman-remote`; в многострочном
  `RUN` комментарий съедает остаток строки и ломает продолжение (строка,
  начинающаяся с `&&`, → syntax error).
- **verify-before-fix.** Фикс, основанный на диагностике (своей или суб-агента),
  — только после верификации фактического утверждения дешёвой read-only-проверкой
  (`dnf provides`, `--version`, логи и т.п.). Ограничение «не вносить изменений»
  не распространяется на read-only проверки: проверять всегда можно и нужно.
  Неверифицированное утверждение — гипотеза: подавать как гипотезу, а не как
  причину.

## Логи llama-server (llama-cpp)

- Таймстемп строки лога — `мм.сс.ммм.ммм`: минуты и секунды с момента
  старта процесса instance (две трёхзначные дробные группы), не время
  суток. Пример: `17.26.039.187` = 17 мин 26.039 с после старта instance.
  Сверка: разница launch→release task ≈ `total time` из print_timing;
  wall-clock — по STIME в `ps -ef` в контейнере. Часы: контейнер —
  UTC, хост и toolbx — MSK (UTC+3).
- Префикс `[NNNNN]` в строке — порт instance (не pid). pid 1 — router
  (`--models-preset`), instance — единственный потомок pid 1
  (`ps -ef | awk '$3 == 1 {print $2}'`).
- `podman-remote logs llama-cpp` — только текущий контейнер (юнитовый
  `ExecStartPre` удаляет его); постоянная история — `journalctl -lu
  llama-cpp [--since ...]`. Нумерация task в каждом новом instance
  начинается заново.
- Один HTTP-запрос клиента (один LLM-вызов) = один task; длинный
  агентский ход = цепочка task на том же слоте (слот выбирается по
  LCP-сходству кэша: «selected slot by LCP similarity»).
- Контекст сессии может мигрировать между слотами (в т.ч. при
  вытеснении слота другим запросом): cache-ram делает restore без
  ре-префилла (в логе — дельта-префилл на новом слоте, а не полный).
  Вытеснение живого контекста занимает секунды (144k ≈ 9 c), новый
  запрос может ждать его в очереди; после вытеснения сессия
  восстанавливается из RAM без потерь.

## Живой сервер (llama-cpp)

Перед первым действием над живым llama-cpp-сервером (рестарт/стоп/старт,
ключи, sysconfig, контейнер/юнит, прод-логи) — прочитать
`LIVE-SERVER.md`.

- VRAM: 5×RTX 3060 12GB = 60GB суммарно (tensor-split). `ctx-size 430000`
  (2×215k) — рабочий потолок (58.3/60GB); `470000` — OOM в обоих режимах
  (unified и non-unified, 2026-09-02). `cache-ram 131072` (128GB) —
  верифицирован: restore без ре-префилла, 0 эвикшенов при 3 крупных
  сессиях. Отчёт:
  `docs/superpowers/reports/2026-09-02-cache-ram-verification.md`.
